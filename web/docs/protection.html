abuse protection

Every public IRC server is scanned within hours of going online. Botnets and drone networks connect by the hundreds to flood channels, spam users and probe for open proxies, and plain scanners open and drop sockets just to fingerprint you. SekurIRCd ships with several layers that stop most of this before a client ever registers, with no external services or extra processes.

why it matters

  • Drones and proxies hide the attacker. Most flood and spam traffic arrives through open proxies or infected machines, so banning by nick or hostmask after the fact does little. Blocking the address at connect time does.
  • Cheap for you, costly for them. A refused connection uses almost no resources, while a fully registered flood client joins channels, fires off WHOIS/LIST storms and burns CPU.
  • Protects your real users. Bans happen at the socket, before any user or channel is touched.

dnsbl checking

A DNSBL (DNS blocklist) is a DNS zone that answers "is this IP known-bad?". SekurIRCd reverses the connecting IPv4 address, looks up d.c.b.a.<zone> on a worker thread, and treats any answer as "listed". Lookups never block the main loop: the new connection is simply held, with no input read, until the verdict arrives. IPv6 addresses are not checked, and a zone that does not answer fails open, so the connection is let through.

No zone is hardcoded, so a provider changing its policy can't surprise you. The shipped template enables the check with the EFnet RBL, an IRC-focused list of open proxies, drones and spamming hosts with no query-volume restrictions.

enable and configure

[dnsbl]
enabled = true
zones = ["rbl.efnetrbl.org"]        # checked in order; first hit wins
timeout = 5.0                       # seconds per lookup before "not listed"
action = "kline"                    # "kline" or "reject"
kline_duration = "1d"               # "1d", "12h", "30m", or seconds; "" = permanent
#lookup_url = "https://dronebl.org/lookup?ip={ip}"   # optional link added to the ban reason
  • enabled = true needs at least one zone, otherwise the config is rejected at load. If you remove the whole [dnsbl] section, the check stays off.
  • action = "kline" refuses the connection and records a ban for that IP, so repeat attempts are refused without another DNS lookup. "reject" only refuses that one attempt and leaves no lasting ban.
  • Keep kline_duration short (the default is one day). Dynamic IPs get reassigned, and a permanent ban from a single listing is rarely right.
  • Add more zones only after confirming they are still live and accept your query volume; a dead zone just times out silently. The template comments weigh Spamhaus ZEN (email-focused, licensing limits), Tor exit lists (blocks every Tor user) and DroneBL (its public DNSBL was shut down in 2021, not recommended).

To see whether an address is listed, reverse its octets and query the zone yourself: dig +short 4.3.2.1.rbl.efnetrbl.org checks 1.2.3.4. Any answer means listed; no answer means clean.

connect-flood throttle

Scanners often connect and drop faster than a concurrency cap can see. This tracks connections per IP over a time window; once an IP exceeds the limit it is banned automatically and told reconnecting too fast.

[security]
connect_flood_max = 5                 # more than this many connects...
connect_flood_window = 10.0           # ...within this many seconds -> ban
connect_flood_kline_duration = "10m"  # "" or 0 = permanent; connect_flood_max = 0 disables the check

Raise connect_flood_max if many legitimate users share one NAT'd IP, such as a school, an office, or a web gateway like Kiwi in front of your server.

connection caps

[security]
max_connections = 0            # total simultaneous connections; 0 = unlimited
max_connections_per_ip = 0     # per single IP; 0 = unlimited

Both default to unlimited. Set them on any public server; a per-IP cap of 3 to 5 suits most networks, higher if gateways or shared NATs front real users. Refused connections get a plain ERROR before registration.

bans: k-line, g-line, z-line

All three ban by IP mask, are enforced before registration, and disconnect matching clients that are already online. Automatic bans from DNSBL hits and the connect-flood throttle are recorded as Z-lines (a pure-IP ban applied before registration), tagged with what set them: dnsbl or connect-flood.

/ZLINE 198.51.100.7 1d :abuse from this host    # add: mask, optional duration, reason
/ZLINE                                          # no arguments: list active lines
/UNZLINE 198.51.100.7                           # remove
/STATS z                                        # also /STATS k, /STATS g, /STATS l

KLINE/UNKLINE and GLINE/UNGLINE take the same arguments. Durations are 30m, 12h, 1d, or omit for permanent. Set [security] klines_file so bans survive REHASH and restarts; without it they live in memory only.

What each letter matches. ZLINE is enforced at accept(), before the client has sent anything, so it can only ever match the IP — that is why the DNSBL and connect-flood auto-bans use it. KLINE and GLINE additionally match user@host, so *.example.com or bob@*.example.com do what they look like they do. Since a hostname isn't known until rDNS/ident finish, a host mask is checked again at the end of registration rather than at connect time. The ident is tried both bare and ~-prefixed, so a mask bites whether or not identd answered.

False positives: a legitimate user who is on a DNSBL can be freed with UNZLINE, but their next connection triggers a fresh lookup and bans them again, since there is no allow-list. The reliable fixes are dropping that zone, or using action = "reject" so no lasting ban exists and pointing the user at the provider's delisting page, which is what lookup_url is for.

monitoring

server notices

Opers get user mode +s automatically on /OPER and receive a notice for every refused connection, for example Rejected connection from 203.0.113.9: Proxy/Drone detected (rbl.efnetrbl.org), and for every ban added, removed or expired. If it gets noisy during an attack, silence it with /MODE <yournick> -s.

debug channel and log

[debug_channel]
enabled = true
name = "#server-debug"      # oper-only; JOIN is refused to everyone else
min_level = "WARNING"       # DNSBL hits are logged at WARNING, so they appear here
stats_interval = 300        # seconds between summary lines; these are INFO, so also set min_level = "INFO"

Each DNSBL hit is also written to the log ([logging]) as a warning:

dnsbl: 203.0.113.9 listed in rbl.efnetrbl.org -- K-lined

With stats_interval set, the periodic summary tells you how well protection is working (example output):

stats: users=142 (peak 190), channels=61 (18 registered), connections=9314 total,
       lines active=0 K/0 G/37 Z (35 from DNSBL), dnsbl hits=412 total, ircd cpu=0.4% mem=21MB

Watch dnsbl hits and the count of active lines from DNSBL: a steady trickle is normal, and a sudden climb means an attack is being absorbed. If the hit count stays at zero on a public server for weeks, check that the zone still resolves with dig.

recommended setup

[security]
max_connections_per_ip = 4
connect_flood_max = 5
connect_flood_window = 10.0
connect_flood_kline_duration = "10m"
klines_file = "klines.json"          # persist bans across restarts

[dnsbl]
enabled = true
zones = ["rbl.efnetrbl.org"]
action = "kline"
kline_duration = "1d"

[debug_channel]
enabled = true
min_level = "INFO"
stats_interval = 300

Apply with /REHASH. Then open a client as an oper, join #server-debug, and confirm the summary line shows up. See the configuration page and the full template on GitHub for every key.

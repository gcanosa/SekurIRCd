protection bundle

Every public IRC server is scanned within hours of going online. Botnets and drone networks connect by the hundreds to flood channels, spam users and probe for open proxies, and plain scanners open and drop sockets just to fingerprint you. The Protection bundle is SekurIRCd's answer: an optional layer, built into the daemon and configured from a single file, that stops most of this before a client ever registers. No external services, no extra processes.

It is a module you choose to run. Leave the file out and the daemon behaves as a plain ircd; drop it in and edit one place to tune all of it.

why it matters

  • Drones and proxies hide the attacker. Most flood and spam traffic arrives through open proxies or infected machines, so banning by nick or hostmask after the fact does little. Blocking the address at connect time does.
  • Cheap for you, costly for them. A refused connection uses almost no resources, while a fully registered flood client joins channels, fires off WHOIS/LIST storms and burns CPU.
  • Protects your real users. Bans happen at the socket, before any user or channel is touched.

the layers

LayerCatchesSection
Blacklists (DNSBL)Known open proxies, drones and spam hosts listed by a DNS blocklist[blacklist]

turning it on

The bundle is one file, protection.toml, kept next to sekurircd.toml. A fully commented template ships as config/protection.template.toml.

cp config/protection.template.toml /etc/sekurircd/protection.toml
$EDITOR /etc/sekurircd/protection.toml
/REHASH                              # no restart needed
/PROTECT                             # shows what is active
  • The file is optional. Its location is [security] protection_file (default "protection.toml", relative to the config directory; "" never looks for one). With no file, nothing changes from a plain sekurircd.toml setup.
  • It wins over the old keys. The keys that now live in the bundle ([spam], [dnsbl], max_connections*, connect_flood_*, flood_*) are still honoured from sekurircd.toml, so existing setups keep working untouched. When the bundle sets one of them, the bundle's value is used; a key it leaves out keeps its old value.
  • Legacy [dnsbl] keeps working when the bundle defines no zones, and logs a one-time deprecation warning pointing here.
  • VERSION shows the feature flags: D when blacklists are active, P when the proxy scanner is.

blacklists (dnsbl)

A DNSBL (DNS blocklist) is a DNS zone that answers "is this IP known-bad?". SekurIRCd reverses the connecting IPv4 address, looks up d.c.b.a.<zone> on a worker thread, and reads the answer's last octet, the reply code, which says why it is listed. Lookups never block the main loop: the new connection is simply held, with no input read, until the verdict arrives. IPv6 addresses are not checked, and a zone that does not answer fails open, so the connection is let through.

No zone is hardcoded, so a provider changing its policy can't surprise you. The template enables the EFnet RBL, an IRC-focused list of open proxies, drones and spamming hosts with no query-volume restrictions.

configure

[blacklist]
enabled = true
timeout = 5.0                 # seconds to wait before treating the address as "not listed"
action = "zline"              # "zline" | "kline" | "reject"
ban_duration = "1d"           # "1d", "12h", "30m", or seconds; "" = permanent

[[blacklist.zone]]
name = "rbl.efnetrbl.org"
type = "reply"                # "reply": last octet must equal a code below; "bitmask": bit test
ban_unknown = true            # listed with a code that is not below: ban anyway?
reason = "Blacklisted (%r) -- for more information, visit https://rbl.efnetrbl.org/?i=%i"
replies = ["1:open proxy", "2:spamtrap666", "3:spamtrap50", "4:TOR", "5:drones / flooding"]
  • Add one [[blacklist.zone]] per zone. All are queried together, and the first in file order whose rules match decides.
  • replies is what makes a general-purpose list usable: list only the categories you care about and set ban_unknown = false, and everything else is ignored. With no replies, any listing bans. Use type = "bitmask" for lists that combine categories as bits in the last octet.
  • In reason: %i is the address, %t the zone, %r the matched reply text.
  • action = "zline" refuses the connection and records a ban for that IP, so repeat attempts are refused without another DNS lookup, and every other connection from that address is dropped too. "reject" only refuses that one attempt and leaves no lasting ban.
  • Keep ban_duration short (the default is one day). Dynamic IPs get reassigned, and a permanent ban from a single listing is rarely right.
  • Add more zones only after confirming they are still live and accept your query volume; a dead zone just times out silently. The template comments weigh Spamhaus ZEN (email-focused, licensing limits), Tor exit lists (blocks every Tor user) and DroneBL (its public DNSBL was shut down in 2021, not recommended).

To see whether an address is listed, reverse its octets and query the zone yourself: dig +short 4.3.2.1.rbl.efnetrbl.org checks 1.2.3.4. Any answer means listed; the last octet is the reply code.

proxy scanner

A blacklist only knows about proxies somebody already reported. The scanner finds the rest itself. When a client connects, the server opens connections back to that client's address on the classic proxy ports and asks each to relay to this server. If this server's own connect banner (*** Looking up your hostname) comes back through the relay, the address is a working open proxy: it is banned, and so is everyone connected from it.

ProbeWhat it does
httpHTTP CONNECT to this server. The most common open proxy, found on many ports.
httppostAn HTTP POST through a forward proxy. Sends one block of data, but enough of them still make a flood.
socks4SOCKS4 connect request.
socks5SOCKS5 with no authentication, then a connect request.

The scan runs in the background: the client registers and chats as normal until a scan confirms, so honest users never wait on it. It uses non-blocking sockets in the main event loop, not the worker threads, and is bounded three ways: a per-probe timeout, a max_concurrent cap on open probe sockets (a connection flood can't exhaust your file descriptors), and an optional negative cache so a clean address isn't rescanned.

[scanner]
enabled = false               # off by default
action = "zline"              # "zline" | "kline" | "reject"
ban_duration = "1d"
protocols = ["http:80", "http:8080", "http:3128", "http:6588", "httppost:80",
             "httppost:8080", "socks4:1080", "socks5:1080"]
timeout = 10.0
max_concurrent = 256
negcache = "0"                # e.g. "1h": skip addresses that just scanned clean

[scanner.target]
ip = "203.0.113.10"           # THIS server's PUBLIC address (required)
port = 6667

Before you enable it:

  • target.ip must be this server's public address, reachable from anywhere. A proxy on the internet cannot reach 127.0.0.1 or 192.168.x.x, so a private address means the scanner runs and never finds anything. The server logs a warning at startup if the address looks private.
  • It makes outbound connections to arbitrary addresses. Some networks treat that as a port scan and report it to your hosting provider, so check your provider's policy. log_all_scans = true records every probe (at DEBUG, in the log file) as an audit trail.
  • The connections a probe relays back to your server are recognised and exempt from the connect-flood throttle and the per-IP cap, and are never scanned themselves.
  • Try action = "reject" first if you want to watch what it finds before it bans anything.
  • A negative cache trades safety for speed: anyone running a proxy can switch it off for one scan, connect, and switch it back on. Off by default.

Scan an address on demand as an oper with /PROTECT SCAN <ip>.

connection limits

connect-flood throttle

Scanners often connect and drop faster than a concurrency cap can see. This tracks connections per IP over a time window; once an IP exceeds the limit it is banned automatically and told reconnecting too fast.

[connection]
connect_flood_max = 5                 # more than this many connects...
connect_flood_window = 10.0           # ...within this many seconds -> ban
connect_flood_ban_duration = "10m"    # "" = permanent; connect_flood_max = 0 disables the check

Raise connect_flood_max if many legitimate users share one NAT'd IP, such as a school, an office, or a web gateway like Kiwi in front of your server.

connection caps

[connection]
max_connections = 0            # total simultaneous connections; 0 = unlimited
max_connections_per_ip = 0     # per single IP; 0 = unlimited

Both default to unlimited. Set them on any public server; a per-IP cap of 3 to 5 suits most networks, higher if gateways or shared NATs front real users. Refused connections get a plain ERROR before registration.

per-client flood guard

[flood]
max_msgs = 20      # a registered client sending more than this many lines...
window = 1.0       # ...within this many seconds is disconnected

bans: k-line, g-line, z-line

All three ban by IP mask, are enforced before registration, and disconnect matching clients that are already online. Automatic bans from blacklist hits, the proxy scanner and the connect-flood throttle are recorded as Z-lines (a pure-IP ban applied before registration), tagged with what set them: dnsbl, protection (the scanner) or connect-flood.

/ZLINE 198.51.100.7 1d :abuse from this host    # add: mask, optional duration, reason
/ZLINE                                          # no arguments: list active lines
/UNZLINE 198.51.100.7                           # remove
/STATS z                                        # also /STATS k, /STATS g, /STATS l

KLINE/UNKLINE and GLINE/UNGLINE take the same arguments. Durations are 30m, 12h, 1d, or omit for permanent. Set [security] klines_file so bans survive REHASH and restarts; without it they live in memory only.

What each letter matches. ZLINE is enforced at accept(), before the client has sent anything, so it can only ever match the IP — that is why the blacklist, scanner and connect-flood auto-bans use it. KLINE and GLINE additionally match user@host, so *.example.com or bob@*.example.com do what they look like they do. Since a hostname isn't known until rDNS/ident finish, a host mask is checked again at the end of registration rather than at connect time. The ident is tried both bare and ~-prefixed, so a mask bites whether or not identd answered.

False positives: a legitimate user who is on a DNSBL can be freed with UNZLINE, but their next connection triggers a fresh lookup and bans them again, unless the address is under [exempt]. The reliable fixes are that exemption, dropping the zone, narrowing it with replies and ban_unknown = false, or using action = "reject" so no lasting ban exists and pointing the user at the provider's delisting page, which is what %i in the ban reason is for.

spam protection

The layers above act on connections. [spam] acts on what a connected user sends. It is off by default (enabled = false); when off, none of it runs. It has three independent layers:

  1. New-connection restriction. A fresh connection cannot PM users for new_user_period (default 30s). Channels stay open, and anyone can always message services and opers, so nobody is locked out of asking for help.
  2. Content filters. Regex rules from filters_file (an annotated example ships as config/spamfilters.conf) are matched against PRIVMSG/NOTICE to users and channels, and against AWAY, QUIT, PART and TOPIC text. Matching is case-insensitive POSIX ERE, run after mIRC colour and bold codes are stripped.
  3. Recipient and repeat limits. Messaging more than max_targets different people or channels, or sending the same text (8+ characters) to max_repeat of them, inside target_window triggers limit_action.
[spam]
enabled = true
exempt_opers = true          # opers and services are never checked
exempt_identified = true     # neither is anyone logged in to an account
new_user_period = "30s"      # "0" = off
max_targets = 5              # distinct recipients per target_window; 0 = off
target_window = "30s"
max_repeat = 4               # same text to this many recipients; 0 = off
limit_action = "block"       # block | warn | kill | zline
zline_duration = "1h"
trust_age = "0"              # connections older than this skip the limits (not the filters)
filters_enabled = true       # false keeps the file but stops using it
filters_file = "spamfilters.conf"

filter rules

One rule per line: <targets> <action> <duration|-> "<reason>" <regex>. Targets are letters: p PRIVMSG to a user, c PRIVMSG to a channel, n/N NOTICE to a user/channel, a AWAY, q QUIT, P PART, t TOPIC. The first matching rule wins.

ActionEffect
blockDrops the message and tells the sender. QUIT and PART reasons are silently replaced with a blank one.
warnDelivers the message but notifies opers. Use it to trial a rule before enforcing it.
killDisconnects the sender.
zlineDisconnects the sender and Z-lines their IP for the rule's duration (- means zline_duration).
pcnN block - "advertisement" (buy|cheap) +(viagra|followers|likes)
pc warn - "possible invite spam" (join|server) .*(discord\.gg|t\.me)
qPt zline 1h "advertising in reason" https?://[^ ]+.*(casino|porn)

managing rules live

/SPAMFILTER                                   # list rules (with numbers) and the hit counter
/SPAMFILTER ADD pc block - ad_spam :cheap +viagra
/SPAMFILTER DEL 3

ADD takes targets, action, duration, a reason (underscores become spaces) and the regex, and appends to the filters file. DEL removes the numbered rule from the file and leaves your comments alone. Regexes with backreferences, or that match the empty string, are refused. Editing the file by hand and running /REHASH reloads it; a line that fails to parse is skipped with a logged warning. If filters_file = "", rules exist in memory only.

Scope: enforcement covers this server's own users, and each linked server keeps its own copy of the filters file. Every action sends opers with +s a notice that includes the offending text, which is the easiest way to tune rules and limits.

monitoring

server notices

Opers get user mode +s automatically on /OPER and receive a notice for every refused connection, for example Rejected connection from 203.0.113.9: Blacklisted (drones / flooding) ..., and for every ban added, removed or expired. If it gets noisy during an attack, silence it with /MODE <yournick> -s.

/PROTECT

/PROTECT                 # server opers: what is active, and the counters
/PROTECT SCAN 203.0.113.9

Prints the bundle file in use, the blacklists (zones, action, hits so far), the scanner (probes per client, target, in flight, scanned, proxies found, negcache size), the connection limits, the flood guard and spam protection.

debug channel and log

The bundle needs no notification setup of its own. Everything it does is logged, and the [debug_channel] you already have relays it, so #server-debug doubles as its live feed:

[debug_channel]
enabled = true
name = "#server-debug"      # oper-only; JOIN is refused to everyone else
min_level = "INFO"          # bans are WARNING, the startup summary and stats lines are INFO
stats_interval = 300        # seconds between summary lines
[WARNING] protection: 203.0.113.9 is an open socks5 proxy (port 1080) -- Z-lined for the configured duration, 3 client(s) disconnected
[WARNING] dnsbl: 203.0.113.44 listed in rbl.efnetrbl.org (drones / flooding) -- Z-lined
[INFO] protection: scanner: 8 probe(s) per client [http:80 ... socks5:1080], target 198.51.100.7:6667, action=zline, negcache 3600s, max 256 in flight
[WARNING] protection: scanner.target.ip 10.0.0.5 is a private address -- proxies on the internet can't reach it ...

The startup summary is logged at start and after every /REHASH, so you can confirm what a reload actually turned on. With stats_interval set, the periodic summary tells you how well protection is working (example output):

stats: users=142 (peak 190), channels=61 (18 registered), connections=9314 total,
       lines active=0 K/0 G/38 Z (35 from DNSBL, 3 from scanner), dnsbl hits=412 total,
       proxy scanner: scanned=8817 proxies=3 in-flight=2 negcache=641, ircd cpu=0.4% mem=21MB

Watch dnsbl hits, proxies and the count of active lines from each: a steady trickle is normal, and a sudden climb means an attack is being absorbed. If the hit count stays at zero on a public server for weeks, check that the zone still resolves with dig. Per-probe detail (log_all_scans) goes to the log file at DEBUG, deliberately not to the channel.

recommended setup

# protection.toml
[exempt]
ips = ["127.*"]

[connection]
max_connections_per_ip = 4
connect_flood_max = 5
connect_flood_window = 10.0
connect_flood_ban_duration = "10m"

[blacklist]
enabled = true
action = "zline"
ban_duration = "1d"

[[blacklist.zone]]
name = "rbl.efnetrbl.org"
ban_unknown = true
replies = ["1:open proxy", "2:spamtrap666", "3:spamtrap50", "4:TOR", "5:drones / flooding"]

# sekurircd.toml
[security]
klines_file = "klines.json"          # persist bans across restarts

[debug_channel]
enabled = true
min_level = "INFO"
stats_interval = 300

Apply with /REHASH. Then open a client as an oper, join #server-debug, and confirm the summary line shows up. Add the [scanner] once you have read the notes above and know your public address. See the configuration page and the full template on GitHub for every key.

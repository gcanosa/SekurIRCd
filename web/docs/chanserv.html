ChanServ

bin/chanserv is a completely separate, optional process. It links to the ircd as an ordinary server peer and introduces one bot, ChanServ, that lets a channel be registered behind a password so its ops survive an empty channel instead of going to whoever joins first. Registrations are JSON on disk with rotating backups ([storage] backup_count, default 5); if the live file is corrupt, the newest readable backup loads automatically.

enable it

1. ircd side: turn on linking and add a peer

[links]
enabled = true
mode = "hub"

[[links.peers]]
name = "services.sekurircd.local"
password_hash = "scrypt$16384$8$1$<salt-hex>$<digest-hex>"   # from sekurircd --hash-password

2. services side: point it at the link port

cp services/services.template.toml services/services.toml
# edit [link] host/port to the ircd's [links] bind/port,
# name/password to the [[links.peers]] entry above (the plain secret goes here)

See the full services.template.toml on GitHub for every option, including [storage] backup_count.

run it

./bin/chanserv --config services/services.toml                     # foreground
./bin/chanserv --config services/services.toml --daemon --pidfile services/chanserv.pid
./bin/chanserv --stop --pidfile services/chanserv.pid

A second --daemon against a live pidfile is refused. If the ircd is down or the link drops, ChanServ keeps retrying. Easiest: ./sekurircd start from the repo root starts ChanServ automatically when services/services.toml exists (see install). Under systemd: systemctl --user enable --now chanserv.

commands

/msg ChanServ REGISTER #chan <password>            # you must be opped on #chan
/msg ChanServ IDENTIFY #chan <password>            # every new connection, to reclaim founder status
/msg ChanServ DROP #chan <password>
/msg ChanServ SETPASS #chan <old> <new>
/msg ChanServ JOIN #chan <password>                # GUARD: ChanServ stays in the channel
/msg ChanServ PART #chan <password>
/msg ChanServ TOPICLOCK #chan ON|OFF <password>
/msg ChanServ INFO #chan
/msg ChanServ ACCESS #chan ADD|DEL|LIST [<mask> <v|h|o>] <password>
/msg ChanServ AKICK #chan ADD|DEL|LIST [<mask>] <password>
/msg ChanServ SUCCESSOR #chan SET <mask> <password>
/msg ChanServ SUCCESSOR #chan CLAIM <new-password>
/msg ChanServ SET #chan MLOCK|DESC|URL|ENTRYMSG ...
/msg ChanServ HELP

The password belongs to the channel record; anyone who knows it can IDENTIFY as founder. IDENTIFY lasts for the connection only and must be repeated after reconnecting. /HELP in ChanServ prints exact syntax for each command.

guard and topiclock

JOIN makes ChanServ a permanent member, so the channel can never go empty or be squatted. The setting persists across restarts and ChanServ rejoins immediately if kicked. Each time it (re)joins it deops anyone not identified this session, closing the gap where a full ircd restart lets a stranger win the race to an empty channel. TOPICLOCK records the topic and restores it when GUARD rejoins, since topics live only in ircd memory.

access and akick masks

  • A bare host (trusted.example), ident@host, or a full nick!ident@host. Shorthand is wildcard-expanded. The host is always required, so a nick alone can never grant access.
  • =accountname matches by services account (SASL or /REGISTER) and only after the joiner has identified. This is the right choice under host cloaking and survives IP changes.
/msg ChanServ ACCESS #chan ADD *@trusted.example h <password>   # auto +h on JOIN from that host
/msg ChanServ ACCESS #chan ADD =alice o <password>               # auto +o once alice is identified
/msg ChanServ AKICK  #chan ADD *@bad.example <password>

brute-force protection

Every command that checks an existing password locks that nick out of password checks, network-wide, for a short window after repeated failures. That also stops one nick grinding through passwords across many channels. The lockout clears on QUIT and follows a nick change.
